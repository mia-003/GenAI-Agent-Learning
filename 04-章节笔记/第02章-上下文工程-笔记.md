
上下文是利用现有模型开发高效 Agent 的关键，包括系统性地设计、组织和提供 AI 完成任务所需的全部背景知识。决定 Agent 在业务中发挥价值的往往不是模型参数量，而是它在每个决策点能获得多么丰富、精准的上下文。Agent 的下一步行动取决于截至当前的完整交互上下文，而不只是眼前这一条输入。
## 消息的四种角色
LLM API的核心是消息列表（messages），每条消息都有：
- system（系统提示词），最高优先级指令，由开发者编写，整个对话中只有一条
- user（用户消息）
- assistant（助手消息），模型的回复
- tool（工具结果）

```
%% request场景 %%
  "messages": [
    {
      "role": "system",                // ← Written by developer
      "content": "你是计算助手。有计算工具时优先使用；没有工具时可自行推导。缺少必要输入时先询问用户，不要编造。"
    },
    {
      "role": "user",                   // ← User input
      "content": "请计算 (125 + 375) * 8。"
    }
  ]
```
```
%% API response场景 %%
  "choices": [{
    "message": {
      "role": "assistant",              // ←Generated by model
      "content": "LLM reply contetnt"
    }
  }]
```
当需要调用工具时，模型负责发出调用请求，真正执行工具的是Agent框架。模型负责决策（调用什么工具、传什么参数），Agent 框架负责执行（实际调用 API、执行工具、运行代码、将执行结果和全部会话历史再返回给模型）。比如tool_call_id和content都是Agent框架生成后追加在messages列表中的。
从模型的代码运行来看，本质上是while循环+判断。用while True + if not tool_calls: break来结束迭代。每轮循环要增加message。初始状态的message只有“system”和“user”，第一次模型返回时增加了“assistant”和“tool”，内容分别是模型第一次返回的内容和工具调用的结果，第二次模型返回时再增加“assistant”，内容是模型第二次回复的内容。
